# 系统复杂度诊断与范围收敛

## 结论

项目最初目标是：从上市公司 ESG/年报公开文档中采集数据，抽取指标，按固定规则生成排名。
当前系统已经扩展为：多交易所公司池治理、文档证据审计、80项指标计算、自动预排名、人工单审/双审/仲裁、
发布冻结、增量重算、专利对照实验和正式交付门禁。因此“越来越复杂”不是错觉，而是产品边界发生了变化。

当前的主要问题不是代码质量，而是四种产品混在一个工程里：

1. **数据采集产品**：发现、下载、校验和文本化报告；
2. **研究排名产品**：自动抽取、评分、敏感性分析和预排名；
3. **正式发布治理产品**：主体、文档、审核、签名、冻结和授权；
4. **研发取证/专利平台**：E1/E2/E3/E5实验、对照组、Hash和发明人留痕。

如果不分层，任何一个小需求都会同时触发数据、算法、审核、门禁、API、Demo和专利文档的联动，开发自然失控。

## 必要复杂度

这些复杂度与目标本身直接相关，不能简单删除：

- ESG文档来源多、格式不一，PDF文本、表格、OCR和网页链接需要有效性校验；
- 公司主体、证券代码、A/H关系和ST状态必须避免重复或错配；
- 指标存在单位、分母、报告期、正负向、缺失和不适用差异；
- 排名若要可信，必须能追溯到文档、页码、证据文本和计算参数；
- 公开数据不足以支持“官方复刻”，所以必须区分研究预排名与正式排名。

## 偏离初衷后产生的复杂度

以下内容有价值，但不应阻塞最初的“可运行排名 Demo”：

- 把632家公司全量正式发布作为开发完成前置条件；
- 把43项定性指标的双审、仲裁和签名纳入首个可用版本；
- 同时支持四交易所全市场、港股连续性、A/H合并和历史迁移；
- 在主流程尚未稳定前加入增量重算、证据约束图和多项专利实验；
- 维护 v2 到 v22 大量候选/确认/未决产物，版本文件成为事实上的数据流；
- CLI 已扩展到约60个命令、源码约1.5万行，操作入口远超一个排名系统的必要范围；
- 将外部签名、专利权属和发布授权状态与日常研发流程混合。

## 复杂度的根因

### 1. 没有冻结 MVP 边界

“爬文档并排名”没有被拆成明确的 MVP：公司范围、报告期、指标子集、排名输出和质量声明没有先固定，
导致每次发现新风险都直接扩展主系统。

### 2. 研究域和正式域过早耦合

研究版允许自动推断和缺失策略实验，正式版要求固定算法、审核和签名。两者如果共享状态表、页面和命令，
就会产生大量 `pending/confirmed/unresolved/auto/manual/freeze` 分支。

### 3. 用治理要求解决数据不确定性

很多问题本质是“数据未采集或口径不明”，却被转化为审核门禁、批次门禁和发布门禁，软件复杂度增加，
但数据覆盖并没有同比增加。

### 4. 以版本产物代替稳定数据模型

候选、确认和未决文件不断复制为 v2、v3……v22，说明流水线缺少明确的当前快照、输入版本和变更日志模型。

## 范围收敛方案

### MVP（先交付可演示、可运行的排名系统）

- 固定一个报告期和一个明确公司样本（建议先做25～50家能源上市公司）；
- 先实现可稳定抽取的10～15个定量指标，其他指标显示“未覆盖”，不阻塞运行；
- 自动采集→证据候选→评分→研究排名→HTML/CSV/JSON输出；
- 每个结果带来源文件、页码、Hash、覆盖率和“研究预排名”水印；
- 只保留一个审核入口：高影响或冲突候选人工确认；
- 暂不把正式双签、全量定性、专利实验和632家全市场作为 MVP 完成条件。

### V1（可用于内部业务）

- 扩展到37项定量指标和更大公司池；
- 增加审核工作台、敏感性分析和企业证据下钻；
- 研究域与正式域使用不同输入快照和算法版本；
- 正式发布仍由明确授权后单独执行。

### V2（正式交付/审计版）

- 完整公司池、43项定性指标、双审仲裁、发布冻结和授权签名；
- 只有在客户确认公司池、算法、缺失规则和审核资源后启动；
- 专利实验作为研发证据链独立维护，不再阻塞研究排名产品的日常迭代。

## 判断标准

今后每个新功能先回答：它是否直接提高“文档采集成功率、证据准确率、排名可复现性或用户决策效率”？
如果只是提高正式审计完备性、专利材料完整性或未来扩展性，应放入 V1/V2，不得自动进入 MVP 主路径。
