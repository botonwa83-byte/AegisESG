# 系统 Demo 产品化差距与重设计

## 结论

当前 Demo 的底层能力是真实的，但产品表达不合格。它更像“研发可观测性页面”，而不是一个可交付、
可操作、可解释、能支持科学决策的评价系统。原因不是缺少更多排名表，而是没有把“问题—证据—判断—
风险—行动—授权”串成一个决策闭环。

## 当前 Demo 的具体问题

1. 以页面和文件为中心，而不是以领导、数据审核人、方法论负责人三个角色的决策任务为中心；
2. 展示了统计结果，却没有展示一个公司为何得到该结果、哪些证据最关键、哪些缺口会改变名次；
3. 有审核分层，但没有“待办任务—查看证据—形成决定—影响重算—关闭任务”的可操作流程；
4. 有正式门禁，但只是状态数字，没有告诉用户下一步由谁处理、处理什么、通过标准是什么；
5. 原始数据、研究预排名、审核候选和正式排名虽然在代码中隔离，UI中没有清晰的状态边界；
6. 没有一个完整的端到端场景，让用户看到一次真实数据从报告页到指标值、指标分值、综合分和审核风险的链路；
7. 没有面向领导的决策输出，例如“本轮是否可发布”“最值得审核的10项”“排名稳定性是否足够”“若缺口补齐
   会影响哪些公司”。

## 正确的 Demo 定位

Demo 应该是一个“ESG科学决策驾驶舱”，而不是排名浏览器。它需要让用户在十分钟内回答：

- 当前数据是否足以支持决策？
- 哪些公司和指标最值得优先审核？
- 每个结论的证据和计算链能否复核？
- 缺失和口径冲突会不会改变排名？
- 当前能否发布？如果不能，最短补齐路径是什么？

## 重设计后的页面结构

### 1. 决策总览

首屏只展示决策状态：研究预排名、正式发布状态、数据可信度、前200边界稳定性、待处理高风险任务、
预计补齐路径。显示“可发布/不可发布”的理由链，而不是只显示数字。

### 2. 证据与计算链

选择一家公司后，按“报告—页码—证据文本—候选值—单位/主体/年份约束—确认值—标准化分—指标贡献—综合分”
展开。所有缺失、冲突和派生值都要能回到原始证据。

### 3. 风险审核工作台

展示按排名影响排序的待办队列。每条任务提供冲突对照、审核建议、可能名次变化、操作动作和审计记录。
演示环境可以使用“模拟决定”展示重算，但必须标明simulation，不得写入正式观测或伪造签名。

### 4. 方法论与敏感性

展示指标定义、权重、缺失策略、薄样本警告，以及三种策略下的名次区间；用户应能看到“如果不补数据，
这个结论有多稳”，而不是只看到单一名次。

### 5. 正式发布控制台

展示主体门禁、文档门禁、定量门禁、定性门禁、审核门禁、冻结门禁六个状态；每个未通过门禁都显示责任
输入、验收标准和下一步动作。发布按钮在当前状态明确禁用。

### 6. 决策报告

一键生成面向领导的摘要：样本范围、关键发现、排名稳定性、风险项、待审核任务、不可发布原因和可复现
信息。报告必须携带研究/正式状态水印。

## 必须保留的科学性边界

- 预排名、正式排名和模拟审核三种状态必须有显著不同的颜色、标签和数据域；
- 所有自动推断都要显示证据等级和缺失策略；
- 模拟动作不得改变正式输入、签名或发布状态；
- 任何结论都必须可以追溯到证据和版本Hash；
- 领导看到的是决策依据和不确定性，不是为了“好看”而隐藏缺口的名次。

## 验收标准

只有当演示者能够在一个真实公司案例中完成“找到风险任务—查看证据—查看计算—比较敏感性—说明为何
不能发布—给出下一步补齐动作”，并且全程不打开原始JSON或代码页面时，才称为“系统 Demo 完成”。
